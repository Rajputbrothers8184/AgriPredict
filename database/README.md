# Database — AgriPredict

**Owner:** Member 4 (Database Engineer)
**Consumers:** backend (`backend/`), ML service (`ml/`)

This folder is the authoritative definition of the data model. The backend's
SQLAlchemy models mirror these definitions exactly; a parity test
(`database/tests/test_schema_parity.py`) fails the build if they drift.

```
database/
├── schema/       001_schema.sql      canonical PostgreSQL DDL (single source of truth)
│   └── README.md                    table-by-table documentation
├── migrations/   NN_*.sql            ordered, re-runnable-with-care migrations
├── seed/         *.sql               reference data (commodities, markets)
├── diagrams/     erd.md              Mermaid ER data model + relationship notes
└── tests/        test_*.py           parity, constraint and seed-idempotency tests
```

## Supported engines

| Engine | Use | Notes |
| --- | --- | --- |
| SQLite 3.35+ | local development, unit tests, on-device cache | zero setup; `NUMERIC` stored as REAL, so money math is done with `Decimal` in the app layer |
| PostgreSQL 14+ | shared / production deployment | canonical DDL targets PostgreSQL |

Both are supported because a fresh clone must run with no database server, while
a team deployment needs concurrent access.

## Conventions

- **Primary keys:** `INTEGER GENERATED BY DEFAULT AS IDENTITY` (SQLite:
  `INTEGER PRIMARY KEY AUTOINCREMENT`).
- **Timestamps:** `TIMESTAMPTZ`, default `now()`, `updated_at` maintained by the
  application layer (portable across engines).
- **Money:** `NUMERIC(12,2)` in **PKR**. Prices are always **PKR per 40 kg
  (maund)**, the unit used in Pakistani mandis, and the column comment records
  it. Quantities are kilograms. Never store a bare "price" — always with a unit.
- **Enumerations:** stored as `VARCHAR` with a `CHECK` constraint rather than a
  native `ENUM`, so new values are a one-line migration on both engines.
- **Soft deletes:** not used. History matters, so financial rows are immutable
  (corrections are new rows); a user delete cascades deliberately.
- **Naming:** `snake_case`, plural table names, `<table>_<column>_fkey` style
  constraints, index names `idx_<table>_<columns>`.

## Applying the schema

**Fresh database (recommended):**

```bash
psql -d agripredict -f database/schema/001_schema.sql
psql -d agripredict -f database/seed/001_commodities.sql
psql -d agripredict -f database/seed/002_markets.sql
```

**Existing database — apply migrations in order:**

```bash
for f in database/migrations/*.sql; do psql -d agripredict -v ON_ERROR_STOP=1 -f "$f"; done
```

**SQLite / application-managed:** do not apply the PostgreSQL DDL by hand. The
backend creates the schema from its ORM metadata (or Alembic) so the types stay
portable:

```bash
cd backend && alembic upgrade head
```

## Backup and recovery

| Scenario | Procedure |
| --- | --- |
| PostgreSQL logical backup | `pg_dump -Fc agripredict > agripredict_$(date +%F).dump` |
| Restore | `pg_restore -d agripredict --clean --if-exists backup.dump` |
| SQLite backup | `sqlite3 agripredict.db ".backup 'agripredict_$(date +%F).db'"` |
| Verify a backup | restore into a scratch database and run `pytest database/tests` |
| Retention | daily dump kept 14 days; before every release, tag a dump alongside the release |

Automate the dump with cron/Task Scheduler; keep dumps **out of Git**.

## Security

- The application connects with a least-privilege role (`agripredict_app`):
  `SELECT, INSERT, UPDATE, DELETE` on application tables, no DDL, no superuser.
- Every record table is reachable only through the owning `user_id` chain; the
  backend enforces this with per-request ownership filters (see `SECURITY.md`).
- Passwords are stored only as bcrypt hashes in `users.password_hash`.
- Refresh tokens are stored as SHA-256 hashes, never plaintext.
- API keys for weather/Places are **not** stored in the database.
- Row-level security is not enabled (single-tenant academic deployment); the
  application layer is the enforcement point. This is recorded as a limitation.

## Testing

```bash
cd database && python -m pytest tests -q
```

Checks performed: ORM ↔ SQL parity (tables, columns, nullability, uniques),
constraint enforcement (uniqueness, checks, cascade deletes), seed idempotency,
and that the DDL parses as valid SQLite where applicable.
